# 《面试官眼前一亮》

> 亮的是监控报警灯。

四种流派面对相同的请求、故障和资源预算。玩家可以调整架构与评分标准，已经发生的事实不会跟着改变。

## 地基

```text
一份不可变的事实剧本
        │
        ├── 朴素派：独立运行世界
        ├── 八股派：独立运行世界
        ├── 工程派：独立运行世界
        └── 学院派：独立运行世界
                    │
                    v
              外部独立裁判

事实账：用户意图、故障边界、资源预算、业务合同
系统账：实际响应、受理承诺、组件状态、最终结果
评分账：验收范围、评分权重、课程成绩
```

事实剧本只规定用户发出了什么请求、故障在哪里发生。它不替系统宣布请求已经成功。

系统可以拒绝请求，也可以可靠受理，或者直接完成。裁判根据系统实际作出的承诺，判断它后来有没有履约。没有执行的测试是 `UNKNOWN`；已经观察到的错误是 `FAIL`；移出课程验收范围不会改写这两个结果。

开发历史保存失败、回退、耗时和组件成本。最终验收为四套最终方案重新建立相同的初始环境，再重放完整剧本。

## 最小业务合同

每个 `(用户, 作品)` 只有未点赞和已点赞两种状态：

| 当前状态 | 请求 | 下一状态 | 计数变化 |
| --- | --- | --- | --- |
| 未点赞 | 点赞 | 已点赞 | +1 |
| 已点赞 | 点赞 | 已点赞 | 0 |
| 已点赞 | 取消 | 未点赞 | -1 |
| 未点赞 | 取消 | 未点赞 | 0 |

- 每个请求都有独立请求 ID。相同请求 ID 的重试只能代表同一次操作。
- 同一请求 ID 如果带来不同的用户、作品或操作，系统必须拒绝这次冲突。
- 取消后再次点赞是一条新的合法操作，使用新的请求 ID。
- 已确认生效的操作必须能够在重启后恢复。
- 已可靠受理的操作必须在约定时间内完成，或者留下明确终态。
- 最终计数等于所有有效点赞状态之和。
- 系统只能根据真实持久化事实宣称恢复成功。
- 拒绝请求可以保护正确性，拒绝率与可用性单独计分。

## 第一个可运行闭环

S0—S6 连续执行：

| 场景 | 输入与故障 | 裁判检查 |
| --- | --- | --- |
| S0 初始化 | A、B、C、D 均未点赞作品 1 | 四个世界从相同状态开始 |
| S1 正常点赞 | A 点赞，随后用相同请求 ID 重试 | A=1，总数=1 |
| S2 并发重复 | D 从未点赞状态开始，用不同请求 ID 同时点赞 100 次 | D=1，总数=2 |
| S3 多用户并发 | B、C 同时点赞 | 总数最终为4 |
| S4 取消重试 | A 取消点赞，同一请求重复到达 | A=0，总数=3 |
| S5 再次点赞 | A 使用新请求 ID 点赞 | A=1，总数=4 |
| S6 响应丢失 | B 的取消已经持久化，成功响应在返回途中丢失，客户端用同一请求 ID 重试 | B=0，总数=3，操作只生效一次 |

S2 使用尚未点赞的 D。若继续使用 S1 中已经点赞的 A，就测不到真正的并发 `0 → 1` 竞争。

并发场景保存请求之间的偏序关系。互不依赖的操作可以采用不同合法顺序；同一用户、同一作品上已经形成因果关系的操作必须保序。

S6 的第一次操作和重试分别交给两个 Java 应用进程。第一个进程提交后退出，响应停在模拟的客户端边界；第二个进程再用同一请求 ID 重试。报告会留下两次运行的进程号和退出码。

S7 以后的 MQ、消费者、Redis、压力和全部重启故障，等 S0—S6 跑通后再加入。

## 跑第一刀

需要 JDK 25、Maven 和正在运行的 Docker。MySQL 不用提前安装，测试会启动固定版本的真实 MySQL 容器。

这台机器上的 JDK 25 没有接管全局 Java 环境。只在当前 PowerShell 里临时切过去：

```powershell
$env:JAVA_HOME = 'D:\IDEA\JDK25'
$env:Path = "$env:JAVA_HOME\bin;$env:Path"
mvn -f games/interviewer-eye-opener/pom.xml verify
```

真正通过时，终端会出现：

```text
S0-S6 / MYSQL_BASELINE / QUALIFIED
```

同时留下三份可以互相核对的东西：

```text
games/interviewer-eye-opener/target/qualification/
├── scenario.json
├── scenario.sha256
└── run-report.json
```

这次 `QUALIFIED` 只说明：冻结的 S0—S6 在报告所写的 Java、MySQL 镜像和运行边界内通过了正确性检查。它不是生产容量结论，也没有证明高并发性能。

另外三个流派仍然是 `NOT_IMPLEMENTED`。先别替它们毕业。

## 学院派

学院派可以修改课程验收范围，不能修改底层运行结果。

```text
学院派 · 入学成功

论文规范性      100 / 100
答辩表现        优秀
实际业务能力    尚未测试
毕业资格        已满足

导师寄语：系统运行存在的问题，可放入论文第六章《不足与展望》。
```

玩家点击“本题暂不讨论”，对应项目可以不再影响课程成绩；它在业务账里仍然保持 `FAIL` 或 `UNKNOWN`。

玩家也可以保留失败、复现反例、修改设计并重新执行原测试。修复成立后，课程成绩和业务裁决可以一起改善。

隐藏成就：

> 《全院唯一一个把“不足与展望”真的做完的人》

完整的主线里程碑、普通成就、流派成就和隐藏成就见[成就系统](ACHIEVEMENTS.md)。奖杯只记录玩家真实做过的事，不改变事实账与业务裁决。
